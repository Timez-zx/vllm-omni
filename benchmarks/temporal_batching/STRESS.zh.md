# 压测对比:原版引擎 vs 周期优化引擎

**日期**: 2026-08-12 · **分支**: `temporal-batching`
**问题**(用户目标):足够多用户压测,对比两个引擎的**最大可满足用户数(容量)**与**对应延迟**。

## 一、被比较的两个引擎

| | A 原版 | T 周期优化 |
|---|---|---|
| 调度 | vLLM v1 原生贪心 continuous batching(tick 代码全关) | 80ms 全 stage 屏障 + 拍内子格 + lead 缓冲追赶 |
| 引擎循环 | 自由跑 | tick 心跳(WP1:事件间睡眠,输入随到随醒) |
| 传输 | save 线程 + 轮询 | 内联发送(WP4-lite)+ 消费点 80ms 时刻表 |
| 部署 | **同一份** deploy_temporal_2gpu_mns56.yaml,同硬件同种子 | 同左 |

**已实现进 T 臂**:WP1 引擎心跳、WP2(以屏障计划实现)、WP3 部分(talker
CUDA graph 天然命中 uniform decode)、WP4-lite 内联发送、WP6 QoS 门。
**明确未实现**(见 TICK_ENGINE_PLAN.zh.md):WP3 的 attention advance/
事件期输入计划编译、完整定相信箱(双槽位环形 shm)、WP5 输入编码器流式化。

**负载**:每用户真实通话形态——音频 80ms/块流式输入 3s、视频 480ms/帧
常开、长回答(~26s 音频/轮)、思考 2-6s、6 轮/session。QoS 门:
deadline miss < 1% 且 TTFA p99 < 2s 且交付 RTF ≥ 0.98。

## 二、容量结论(稳定包络内,数据干净)

| 并发用户 | A 原版 | T 周期优化 |
|---|---|---|
| 16 | ✅ 通过(TTFA 439/900ms,miss 0.06%) | ✅ 通过(TTFA **315/640ms**,miss 0.02%) |
| 24 | ❌ **失败**:TTFA p99 = **20.8s** | ✅ 通过(TTFA 371/**966ms**,miss 0.30%)† |
| 32+ | 测量被共有稳定性 bug 封顶(见第四节) | 同左 |

† T 的 24 档两次运行均在 cell 内遭遇两臂共有的既有 bug(首跑:mrope 崩溃,
114/144 轮存活;重跑:尾部集体挂起,120/144 轮存活);存活轮次全部通过
QoS。A 的 24 档 144/144 干净完跑,20.8s 尾部为真实调度行为。

**容量:A = 16 用户,T = 24 用户(+50%),且 T 在自己的容量点上延迟
优于 A 在其容量点上的延迟**(T@24: 371/966ms vs A@16: 439/900ms,
抖动 1.15 vs 2.36)。

**对应延迟全景**(16/24 档,干净数据):

| 指标 | A@16 | T@16 | A@24 | T@24 |
|---|---|---|---|---|
| TTFA p50 / p99 (ms) | 439 / 900 | **315 / 640** | 594 / 20,801 | **371 / 966** |
| gap p99/p50(抖动) | 2.36 | **1.11** | 2.34 | **1.15** |
| 卡顿 (ms/轮) | 2.95 | **0.24** | 66.4 | **8.7** |
| deadline miss | 0.06% | 0.02% | 0.66% | 0.30% |
| 交付 RTF | 2.89 | 1.02 | 2.20 | 1.02 |

## 三、机制解剖:A 在 24 用户的 20.8 秒尾部是什么

144 轮里 20 个 >2s TTFA 的轮**全部落在同一个 9 秒窗口**(跨轮堆积:慢用户
的第 5 轮撞上快用户的第 6 轮;各轮提问离散度随时间增大 2.5→15.1s,
说明是概率性撞车而非相位锁定)。贪心逐爆发串行服务这次堆积——队尾等
20+ 秒,教科书车队效应。T 臂在**相同的到达离散度**下:>2s 的轮 **0 个**,
p99 0.79s——pacing 让 24 路并发各自 1× 实时平行推进,车队不形成。

原理链(详见 workflow 第 28 节):超过实时的生成速度对用户价值为零 →
贪心的速度优势在此负载下全额作废,而其代价(抢跑挤占他人首帧、爆发
排队、尖峰需求、节奏靠运气)全部真实;pacing 将零价值速度兑换为
TTFA/尾延迟/抖动/容量,无交换条件。

## 四、稳定边界(诚实声明):32+ 用户被两个共有 bug 封顶

每 cell 独立引导重跑后确认,**两臂在 32-40 用户同样跪**:

| cell | 结果 |
|---|---|
| A u32(重跑) | 74 超时 + 引擎死亡:talker `CUDA device-side assert`(codec embedding 越界 id 家族——async_scheduling 已关仍触发,另有脏 id 路径) |
| T u32(重跑) | 73 超时 + 引擎死亡(存活轮 QoS 通过:p99 1.15s,miss 0.42%) |
| T u40(重跑) | 119 超时,引擎存活:大量 `segment boundary NEVER ARRIVED`(高并发下段结束信号丢失) |
| T u24(重跑) | 全体 session 最后一轮集体挂起(24 超时;engine 活,pipeline 停摆) |

另有已修复的一个:mrope_positions 越界(流式换段后 runner 侧状态未刷新)
——曾在首轮压测同点杀死两臂,已加防御补丁(缺口线性填充 + 告警),
根因(prompt 替换路径刷新 mrope 状态)留待上游。

这些是 vllm-omni 流式 session 机制的**既有健壮性上限**,与调度策略无关
(A 臂纯基线代码同样触发)。在 32/40 档的**存活轮次**上,T 的延迟形态
依旧完好(TTFA p99 1.15/1.30s、抖动 1.17/1.25、RTF 1.02),A@32 则
miss 8.83%、卡顿 311ms/轮、抖动 2.33——方向与 16/24 档一致,但不作为
容量结论引用。

**输出质量**:四个干净档 0 空文本、0 零音频、字/秒比 15.6-15.9 零离群;
A/T 同用户同轮次在上下文未分叉时文本逐字一致(temp=0 确定性成立);
跨臂后期文本差异为"摄像头效应"(T 轮次墙钟更长 → 下一轮画面上下文
不同),非质量问题。质量异常仅出现于已知挂起 cell(3 空文本)。

## 五、复现

