# Temporal Batching 实验结果

**日期**: 2026-08-12 · **分支**: `temporal-batching` · 设计见 `DESIGN.zh.md`

部署:thinker 独占 GPU0(KV 池 275k tokens),talker+code2wav 共 GPU1
(KV 池 1.14M tokens),两 stage 均 `async_scheduling: false`(含基线,保证
四个条件比的是调度策略本身)。负载:engine 直连 session 模式,音频输入
80ms/块流式(12.5Hz),视频 480ms/帧骑音频格,thinker temp=0(各 arm 回复
长度 p50 1.82–2.14s,紧密一致,对比干净),每 cell 10 轮/人、丢弃前 2 轮。

条件:**A** 贪心基线 · **B** tick=80ms · **C** tick=160ms · **D** 只限速不
量化(消融)。B/C/D 的 pacing 覆盖 thinker(25 tok/s)与 talker(12.5
帧/s = 播放速率),lead 240ms,每轮 initial burst 豁免(talker 4 帧 /
thinker 16 token),prefill 天然豁免。

## 二、逐假设裁决

### H1 抖动可预测性:**成立,且随 N 增强**

贪心的 gap p99/p50 随负载恶化:1.46 (u1) → 2.14 (u4) → 2.51 (u16),
u16 时 p99 gap 已到 123ms(标称 45ms 的 2.7 倍)。pacing 三个 arm 在所有
N 下钉在 1.07–1.22,chunk 到达是节拍器级的(gap p50 ≈ 316ms = 4 帧 ×
80ms 的播放时长,分毫不差)。单轮波形:贪心 5 块 170ms 内倾泻完;tick=80
前两块快(burst+lead 兜住 TTFA),之后精确每 320ms 一块。

### H3 TTFA 有界性:**在测试负载下不成立(方向相反)**

u16:A 的 TTFA p50/p99 = 259/501,B = 307/739。pacing 的 TTFA 尾部反而差
~240ms。原因:这个负载区间贪心的爆发完成得太快(交付 RTF 6.7–7.6),轮与
轮很少真正碰撞,贪心排队之痛没有出现;而 pacing 侧新轮的首块虽有 burst
豁免,但 thinker 25 tok/s 的节流和 tick 对齐仍给尾部加了几十到两百 ms。
**结论方向依赖饱和度**——见第四节。

### H2 吞吐/容量:**闭环负载下不可判定(实验设计层面的诚实结论)**

表中 A u16 吞吐 4.30 vs B 3.69 音频秒/墙秒(-14%)**不是** GPU 容量差异,
是闭环负载模型的产物:pacing 把交付从 0.3s 拉长到 ~1.4s,闭环里轮周期变
长、单位时间发起的轮变少。两个 arm 的 GPU 都远未饱和(贪心交付 RTF 6.7,
意味着 talker 有 ~6 倍余量)。要检验 H2 的"齐步合批摊薄每帧成本→容量更
高",需要把系统推到饱和——本盒 max_num_seqs=20 与短回答负载的占空比
(~2s 音频/7-10s 周期)达不到;见第四节的长回答加压与第五节的边界讨论。

### D 消融(只限速 vs 限速+量化):**这个负载区间没有可测差异**

D 与 B 在 u8/u16 的所有指标都在噪声内(p99/p50:D 1.22 vs B 1.19;TTFA
p99:D 630 vs B 739,D 甚至略好)。tick 量化的理论收益(各 session 同一
时刻可调度→合成大 batch→每帧成本摊薄)只有在步进成本被调度器/kernel 启动
主导、且并发 session 的步进频繁交错时才显形——远离饱和时,batch 1 和
batch 8 的 step 都足够快,合不合批无感。**量化不是免费的**:B u16 出现了
唯一的非零 miss(0.24%,平均 2.2ms/轮 stall)——所有 session 对齐同一格
意味着偶发的慢 tick 会同时影响所有人。

## 三、机制证据([SCHED-STEP] 插桩,talker/stage 1)

**短回答 u8**(每轮 ~2s 音频,占空比低):

| | A 贪心 | B tick=80 |
|---|---|---|
| talker 步进间隔 p50/p90/p99 | 11.9 / 14.8 / **895.7** ms | 15.4 / **79.7 / 81.6** ms |
| batch nreq mean(直方图) | 1.17({1:1632, 2:244, 3:39}) | 1.09({1:1900, 2:138, 3:23}) |
| 每步被停车数 mean | 0 | 1.52 |

两个清晰事实:① **80ms tick 直接印在步进间隔上**——B 的 p90/p99 钉在
79.7/81.6ms(节拍器),A 是 12ms 的爆发步 + 895ms 的轮间空转;② **合批没
有发生**(两边 batch p50 都是 1)——短回答下任意时刻平均只有 ~1.6 个
session 在轮中,齐步合批没有原料。"tick 化"在低占空比下改变的是**节奏**,
不是**批**。

**长回答 u16**(每轮 ~26s 音频,任意时刻 ~12 个 session 同时在轮中)——
合批的直接检验,结果**推翻了"齐步合批"子机制**:

| talker/stage 1 | A 贪心 | B tick=80 |
|---|---|---|
| 步数 / 跨度 | 4473 步 / 109s(40.9 步/s) | **13120 步** / 216s(60.7 步/s) |
| batch nreq mean / p50 / max | **7.09 / 7 / 14** | **2.34 / 2 / 12** |
| 每步被停车数 mean | 0 | 8.93 |
| 步进间隔 p50/p99 | 21.7 / 59.4 ms | 14.4 / 57.7 ms |

- 高占空比下,**原生 continuous batching 自己就把批合大了**(贪心 batch
  p50=7):12 个 session 同时在轮中,它们的解码步自然共批。
- pacing 侧**合批没有发生**(batch p50=2,步数反而是贪心的 3 倍)。释放
  时刻确实对齐到了全局格(数学上验证过:各 session 的 release 都 ceil 到
  同一组 tick 边界),但 talker 的**可调度性**还受 thinker→talker chunk
  到达的门控——chunk 走 save 线程→共享内存→recv 线程轮询,到达相位在
  tick 内散布,一个在 tick 边界还在等 chunk 的请求会在 chunk 到达的瞬间
  (格外的任意时刻)被释放并单独解码。释放格的对齐在下游被解耦了。
- 推论:**B 的所有客户端收益(零卡顿、节拍器、TTFA 反超)都来自限速本身,
  量化目前是惰性的**——这正是 D≈B 的机制解释。且按现状实现,pacing 每帧
  的调度/步进开销更高(更多更小的步),对 H2 的效率论证是**反向证据**。

## 四、长回答加压(u16,~26s 音频/轮)——负载翻转结论的区域

各 arm 回复长度仍然一致(audio_s p50:A 25.9s / B 26.3s)。128 轮全成功。

| u16 | TTFA p50 | TTFA p99 | gap p99/p50 | miss% | **卡顿轮占比** | 交付RTF |
|---|---|---|---|---|---|---|
| A 贪心(短回答,对照) | 259 | 501 | 2.51 | 0 | 0% | 6.69 |
| **A 贪心(长回答)** | **531** | 813 | 2.45 | 0.13 | **10.4%** | **2.68** |
| **B tick=80(长回答)** | **461** | 836 | **1.17** | **0** | **0%** | **1.02** |

占空比抬上来之后(每 session 的音频需求 ×13),贪心开始付出代价:

- 交付 RTF 从 6.7 跌到 2.68——爆发之间开始真实争抢;
- TTFA p50 从 259 涨到 531ms——排队出现了;
- **10.4% 的轮出现播放卡顿**(爆发轮内碰撞:一轮交付中途被别的 session
  的爆发打断,超出了已积累的缓冲)。

同负载下 pacing:交付 RTF 1.02(16 路并发全部贴实时)、**零 miss 零卡顿**、
节奏仍是节拍器(1.17),而且 **TTFA p50 反超贪心 70ms**(461 vs 531)——
H3 的方向在这个负载区间翻转为成立:贪心的排队之痛出现后,pacing 的"每
session 每 tick 只拿一点"反而让新轮的首帧更快挤进来。

## 五、边界与结论

### 逐假设终裁

| 假设 | 裁决 | 依据 |
|---|---|---|
| **H1 抖动可预测性** | **成立,所有负载,随 N 增强** | gap p99/p50:贪心 1.46→2.51(随 N),pacing 恒 1.07–1.22;长回答下贪心 10.4% 轮卡顿 vs pacing 0% |
| **H2 吞吐/容量(齐步合批摊薄成本)** | **不成立(按当前实现)** | 合批未发生(batch p50=2 vs 贪心 7),chunk 到达相位散布解耦了释放格;paced 步数反而 ×3;闭环吞吐差异是负载模型产物,非容量 |
| **H3 新轮首帧有界/公平** | **依占空比翻转**:低占空比反向(p99 +240ms),高占空比成立(p50 反超 70ms,卡顿 0%) | 贪心的排队之痛只在爆发开始互相碰撞后出现 |
| **D 消融** | 量化惰性,限速是全部有效成分 | D≈B 所有指标;机制见第三节 |

### 实验边界(诚实声明)

1. **闭环负载**:pacing 拉长交付→轮速下降,吞吐列不可比。容量裁决需要
   开环/固定到达率负载,且本盒(mns=20、275k thinker KV)推不到贪心的
   饱和悬崖。
2. **合成音频输入**(AM 调制音,非真实语音)+ 合成视频帧;语义由文本
   query 驱动,输入管线的计算负载真实。
3. 单次运行/cell(每 cell 8-16 session × 8-10 轮已给出稳定的分布指标,
   但未做多 seed 重复);async_scheduling 全关(基线同关,内部效度优先,
   绝对值比生产配置略保守)。
4. tick 只测了 80/160ms;thinker TPS 只测了 25。

## 六、v2:全 stage tick 屏障(用户提出的"底层 serving 也按 tick batch 处理")

v1 失败的机制找到后(落后请求 `release<=now` 直接放行→永久脱拍),按用户
的原始构想实现了 **barrier 模式**(`VLLM_OMNI_TEMPORAL_BARRIER=1`):每个
tick 边界开窗,在场请求各领本 tick 配额(talker 1 帧/thinker 2 token),
配额尽即停到下一拍;**中途加入者(chunk 刚到)也压到下一拍**——这一条同时
解决了 chunk 相位散布,不需要动流水线。burst 豁免照旧,TTFA 不受影响。

**E(严格实时配额)**:合批立刻兑现——talker batch p50 = **2 → 11**(max
16 = 全部用户),步进间隔 p50/p90/p99 = **79.6/80.6/81.2ms**(整个 stage
精确按 80ms 心跳),每步交付帧效率追平贪心(6.1 vs 6.9 帧/步)。但暴露新
代价:**miss 5.26%**——配额恰好等于播放速率意味着客户端零缓冲,一次打嗝一
次可闻卡顿,而追赶(2×)只在落后超 1 tick 才触发,恢复太慢。v1 的"脱拍
自由跑"缺陷反而客串了瞬时追赶器。

**E2(追赶目标 = 维持 lead 缓冲)**:`ahead < 0.75*lead` 即给 2× 配额,先
建立 ~240ms 客户端缓冲再回到 1×。结果(u16 长回答,vs 各 arm):

| | A 贪心 | B v1 | E 严格屏障 | **E2** |
|---|---|---|---|---|
| TTFA p50 / p99 | 531 / 813 | 461 / 836 | 387 / 591 | **390 / 673** |
| gap p99/p50 | 2.45 | 1.17 | 1.16 | **1.17** |
| deadline miss % | 0.13 | 0 | 5.26 | **0.08** |
| stall/轮 | 1.22ms(10.4% 轮) | 0 | 131ms | **1.42ms** |
| talker 步数(≈同负载) | 4473 | 13120 | 3414 | 5344 |
| batch p50 / ≥10 占比 | 7 / — | 2 / ~0 | 11 / 65% | 2 / 43% |

E2 在**每一项客户端指标上同时优于或持平贪心**(TTFA p50 -141ms、p99
-140ms、抖动 2.45→1.17、卡顿轮 10.4%→~1%),同时保留了大部分合批(43%
的步 batch≥10,承载大多数帧;nreq=1 的小步来自追赶帧与 burst 豁免,是
下一步可调优的余地)。注:E/E2 的数字来自带插桩日志的 run(有轻微观察者
开销),A/B 无插桩——方向性结论不受影响,严格同条件复测留作后续。

**E3(v3:拍内子格 + code2wav 消费点时刻表)**——"每个消费点各自一张
80ms 时刻表"(用户指示)。追赶单位在 open+k·sub_slot 集合(talker 40ms、
thinker 20ms 子格),code2wav 的新 chunk 压到下一 80ms 格点(每 segment
首 chunk 豁免)。u16 长回答:

| | E2 | **E3** | 贪心参照 |
|---|---|---|---|
| talker 碎步(nreq=1) | 2481 | **1603**(-35%) | 49 |
| 帧效率(帧/步) | 3.9 | **6.6** | 6.9 |
| 步进间隔 p50/p99 | 43/81ms | 41/81ms(40ms 子格可见) | 22/59ms |
| TTFA p50/p99 | 390/673 | 410/663 | 531/813 |
| miss% / gap p99p50 | 0.08 / 1.17 | 0.15 / 1.17 | 0.13 / 2.45 |

**帧效率追平贪心,客户端全指标保持**。剩余 1603 个碎步主要是 burst 豁免
的轮首帧(设计代价,买 TTFA)与错过子格的 chunk 迟到者——继续压缩需要
把传输本身节拍化,即 TICK_ENGINE.zh.md 的 v4b 双缓冲信箱。

### 结论(更新)

**用户的原始构想——输入按节奏喂、底层 serving 按 tick 屏障批处理——是对
的。** v1"每请求释放门"是个不充分的近似(落后即脱拍);v2 屏障 + lead
缓冲追赶后,tick 化在高占空比多用户场景**全面占优**:可预测性、卡顿、
TTFA 三者同时赢,合批与步进心跳按设计出现。仍留两件事:①追赶帧的
intra-tick 二次屏障(消掉 nreq=1 小步,把每帧效率从 3.9 拉回 E 的 6.1
帧/步);②输入侧音频每 tick 增量 prefill(需要 entrypoint + 音频编码器
增量化)——完成后整条链路才是完整的同步数据流。

### 旧结论(v1 时点,保留供对照)

**"按音频周期限速"被证明有效;"按 tick 齐步合批"在当前架构下未兑现。**

对于 video+audio 输入、audio 输出的多用户 streaming 负载:

1. **值得要**:temporal pacing(限速到播放速率 + initial burst 豁免 +
   lead 缓冲)在高占空比多用户场景同时赢下延迟可预测性(节拍器级 cadence、
   零卡顿)和 TTFA(排队消失)。代价只在低占空比场景付(TTFA 尾部
   +100-240ms)——而低占空比场景本来就没有问题需要解决。**按需开关**:
   并发 session 数 × 平均音频占空比超过某阈值时打开 pacing 是合理的
   生产策略。
2. **要兑现合批/效率收益,对齐必须打穿整条 chunk 流水线**:光对齐调度器
   的释放时刻不够,thinker→talker 的 chunk 递送(save 线程、shm 轮询)
   也要挂到同一时钟,否则下游可调度性把相位打散。这是明确的后续工程方向,
   也是这次实验最重要的机制发现。
3. 12.5Hz(80ms)这个颗粒度本身被验证是正确的节奏单位:1 talker token =
   1 codec 帧 = 80ms 在代码层面是精确的 1:1:1,tick=80 与 tick=160 的
   客户端指标无差异(160 的实现即每 tick 放 2 帧)。
