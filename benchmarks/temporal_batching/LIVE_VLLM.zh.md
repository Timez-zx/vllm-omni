# live-vllm:周期性负载的原生引擎重设计

分支 `live-vllm`(基于 temporal-batching,2026-08-13 起)。目标:把六条设计
原则从"补丁"变成"架构"——引擎以拍为执行单位,请求驱动退化为事件处理器。

## 0. 方案选型:重设计什么、复用什么

**结论:翻转控制面,复用数据面。** 从零重写 vLLM 是低效路径:模型 runner、
KV 管理、多模态编码、连接器这些数据面组件与"请求驱动还是拍驱动"无关,全部
保留。要翻转的是控制面——谁决定"这一拍做什么":

```
现状(temporal-batching):请求驱动为脊柱,tick 是七个 env 补丁
  (TICK/BARRIER/ENGINE/REPLAY/MAILBOX/INLINE_SEND/FRAME_TICK)
live-vllm:拍执行器为脊柱,补丁转正为器官;决策只在事件发生
```

依据(实验背书,见 PRESSURE/BUGFIX/TICK_ENGINE 各文档):
- talker 内核活跃仅 29%,每步重复决策/发射在周期负载下是纯浪费;
- WP7 证明收益主要来自"非周期关键路径净空",不是合批本身;
- 声码器 25 帧左上下文重算 = 每有用帧 7 倍冗余,GPU1 实测瓶颈;
- 压缩波(p99 64s)与 KV 超卖冻死的机理都是"非周期工作无配额、容量无结构"。

## 1. 架构:六原则 → 六个组件

| 原则 | 组件 | 位置 |
|---|---|---|
| ① 拍是执行单位 | TickExecutive:每拍重放 cohort 计划,决策仅在成员事件 | stage_engine_core_proc + omni_ar_scheduler(REPLAY 转正) |
| ② 周期/非周期分离 | SlackLedger:每拍先扣解码心跳需求,余量为松弛槽,非周期预填按配额切片 | omni_ar_scheduler.schedule |
| ③ 结构化容量 | AdmissionLedger:引擎发布每拍占用,准入按"再加一人还装得下吗"收/拒,不排队 | 引擎心跳 → video_stream_base 准入 |
| ④ 相位是资源 | PhaseAllocator:admission 发相位;声码 1/K 轮值组;触发抖动纳入相位框架 | ChunkTickGate 升级 + 会话准入 |
| ⑤ 算子带状态 | StatefulVocoder:常驻卷积边界状态,增量解码,消灭左上下文重算 | qwen3_omni_code2wav |
| ⑥ 两个 SLO 两套机制 | 松弛槽内 turn-open 专用道(最新开口优先);节拍保播放 | SlackLedger 的排序策略 |

本分支默认全开(env 仍可显式关闭以做对照):周期性不是可选优化,是架构假设。

## 2. 施工阶段与验收

- **P1 拍执行器默认化**:七个开关在本分支默认 on;REPLAY 语义核查(替代路径

- **P2 松弛槽+专用道**:每拍预填配额 = 拍预算 − 解码需求;跨拍切片;最新
  turn-open 优先。验收:压缩/开口大预填不再挤掉解码拍(心跳 p99 ≤ 基线),
  开口 p50 不升。

- **P4 相位分配器**:声码 1/K 轮值。验收:GPU1 削峰,播放不劣化。
- **P5 有状态声码器**:增量解码。验收:波形与重算路径一致(容差内),
  GPU1 每拍耗时下降。
- **P6 整体对照**:live-vllm vs temporal-batching T 臂,long u32/u48 + v160,
  同 FP8 同真实到达;容量探顶 u56/u64。

## 6. A/A+ 阶梯与 u36 头对头(2026-08-13,用户指定设计)

判据(预注册):去热身后 p99>1.5s 或迟到块>1% 或每轮卡住>50ms,任一即"痛"。
A = 原生 vLLM 语义(全 temporal 器官显式归零,含窗口化声码);A+ = A +
stage0 预填预算 32768 + 音频到达即预填。同 FP8 数据面、同负载(long,480ms
视频,真实到达),阶梯 6/12/24/36。

| | A u6 | A u12 | A u24 | A u36 | A+ u36 | **LV u36** |
|---|---|---|---|---|---|---|
| 开口 p50 (ms) | 260 | 343 | 528 | 737 | 750 | **336** |
| 开口 p99 (ms) | 318 | 525 | 831 | 1,347 | 1,118 | **992** |
| 迟到块 | 0% | 0% | 0.52% | **15.5%** | **13.1%** | **0.32%** |
| 每轮卡住 (ms) | 0 | 0 | 17 | **749** | **552** | **10** |
| 块间隔 p99/p50 | 2.42 | 2.32 | 2.45 | 2.36 | 2.35 | **1.18** |
| rtf(送/播比) | 4.87 | 3.49 | 2.16 | 1.44 | 1.48 | **1.02** |

**读法**:
- 原生 vLLM 的 SLO 悬崖在 24→36 之间:开口没爆(1.35s),**播放合同爆了**
  (15.5% 迟到、每轮 0.75s 断声)——贪心的特征死法:算力够开口,节奏散了;
- **调参救不了**:A+ 只削 15-25%,离 SLO 差数量级——差距姓"设计"不姓"参数";
- 同格 LV:迟到块 1/48、卡住 1/75、开口 p50 快 2.2×,SLO 大余量通过;
- 两个签名证据:rtf 从 4.87(贪心爆冲 5× 实时,囤货再断流)收敛到 1.02
  (逐拍按播放速率交付);块间隔 p99/p50 从 2.4(节奏散)到 1.18(心跳);
- 诚实注脚:LV 的文字交付速率 20.1 chars/s 低于 A 的 26(thinker 限速 25tok/s
  by design,仍远高于语音消耗),非质量损失;LV 在 u48 迟到 4.2% 超出 1% 线,
  故 **SLO 容量:A≈24,LV∈[36,48)**——精确值可补 40/44 两格,K 相位数可调。

## 7. CPU 面解放 + u56 悬崖归因侦查(2026-08-13)

**背景**:天花板探测 u56 崩(迟到 14.2%、卡住 1.4s/轮)而 GPU 仅 40%、KV 富裕。
初判 CPU(火焰图:帧 PIL×3 + 内联 process_inputs + ws 发送共享主循环/GIL)。

**修复(V1-V3,已入库)**:
- V1 媒体子进程池:media_worker.py 按路径启动(仅 PIL/numpy,绕开 spawn
  重导入 torch 的坑),一帧一解码,缩放/过滤特征/PIL 缓存回填全部出 GIL;
  离线 363 帧/s,过滤决策与旧路一致;
- V2 输入预处理(分词+多模态)出 serving 循环(专用线程池);
- V3 [loop-lag] 探针 + 容量格健康闸门(loop-lag p99 / API CPU / GPU util)。

**结果:CPU 治好了,病没好——归因被证伪。** API 进程 206%→64%(p90
362→117),PIL 从火焰图消失,loop-lag 26ms,但 u56 迟到 14.5% 纹丝不动。
(用户的质疑"你能确定是 CPU 吗"被数据坐实。)

**排除清单(全部带证据)**:GPU 算力(40%)/KV/压测客户端(11%)/部署差异
(u48@mns80=3.95%≈mns56 的 4.2%)/引擎三级心跳(talker p99=81ms 恰好一拍)
/主循环(26ms≪240ms 缓冲)/CPU 总量(64%)/投递路径(生产 p99 586ms ≈
到达 p99 604ms——块是晚生产,不是晚投递)。

**现状**:凶手在"生产侧的每 session 节奏"——stage2 调度 pass 心跳健康,
但个别 session 的块滑 1-4 拍(生产间隔谱:主峰 320 正点,尾部 400-640)。
在审:P4 相位轮值在高 N 的滑移(K=1 对照)vs 上游 talker/thinker 供给尾。
诊断工具沉淀:AUDIO-CHUNK 生产时间戳、全 stage 心跳、loop-lag、闸门判据。

**结案(diag6/7)**:凶手 = **生产侧每 session 节奏的拍内碎片化**。证据链:
① 块是晚生产不是晚投递(orchestrator 生产 p99 586 ≈ 客户端到达 604ms);
② 相位轮值只是小从犯(K=1 后尾巴 5.9%→4.5%,miss 18→14%);
③ stage1 批结构:每拍非一个整批而是主批+追赶碎批(pass 中位 nreq 仅
7-11,p90 30-43,每秒 ~20 pass ≈ 1.6/拍)——第 4 帧完成时刻拍内散布,
48 人收得住(生产 p99=402、≥480ms 滑移 0.1%),56 人跨拍累积(586、5.9%)。
这正是 TICK_ENGINE.zh.md 记录在案的未竟项:**追赶帧 intra-tick 二次屏障**。

**目标判定:达成。** "CPU 永远不是瓶颈"——API 进程 206%→64%,PIL 全部出
程,闸门(loop-lag/CPU/GPU)常态化;u56 的墙经仪器证明**不是 CPU,是设计**
(每拍步进整合),正落在"真实 GPU 资源或自己设计"的可测范围内。下一个
设计刀(未动,候令):talker 追赶帧的拍内二次屏障 / 步进整合,预期把
u56+ 的生产尾巴收回 402ms 一线。

## 8. P7 相位锁定流水:实施、判决与八连环取证(2026-08-13)

**实施(已入库)**:三级相位(thinker@k·tick+0 / talker@+30ms / 声码闸门
@+64ms,同源单调钟跨进程重合)+ 货运限载(prefill 切片=实测吞吐 EWMA×拍内
剩余×0.7,相位沿后 18ms 解码禁行区)。envs 入 live 默认表。

**判决(u56)**:机制赢一半——stage0 步进 p99 190→**95ms**(客货分离生效),
生产滑移 5.9→**3.0%**;但客户端迟到 15.9% 未愈,且货运限载付出 TTFA p99
+370ms 的代价。u64:心跳仍全绿(94/85/320)而滑移 14%——pass 层已无可指摘。

**八连环证伪(每环一格实验)**:CPU(修到 64% 无效)→ GPU/KV/客户端/部署
→ 投递(生产侧即晚)→ 相位轮值(K=1 仅 -1.4pp)→ 步进心跳(P7 后全绿)
→ 锯齿/领先帽(滑移成串非冲停交替)→ 文字速率(TPS40 反而 4.2%)→
pacer 押人(u56 held 反而更低)。

**现存首要嫌疑(全部形状吻合,未终审)**:talker 的**停车-唤醒占空比**。
文字分段到货,talker 说完一段即 park(WAITING_FOR_STREAMING_REQ),每个
park→wake 循环耗 1-2 拍;说 3-4 拍停 2-3 拍 = 观测到的持续 60% 产能滑移串;
唤醒延迟随 N 涨 = N 敏感性。kept-但-不产出 与 held 走低同时成立,只有
"不在 running 里"这一种解释。
**候选手术(未动)**:talker 文字前瞻缓冲(段间不停车:在飞文字≥X 即持续
说)/ thinker 发段聚合 / 跨级 lead 步调(thinker 盯"领先 talker 消费位
≥X 秒"配速——原则①在级间的完整形态)。

## 9. 根因终审:u56 悬崖 = 第一次压缩波(2026-08-13,可复现)

**判决证据**(p7_u56 与 diag9_u56 两跑波形一致):
- 滑移率时间线:t+0~90s 全程 0%;**t+120s 起爆**(2.4%),t+150s 峰值
  11.5-14.5%,t+180s 8%,**t+210s 后彻底归零**;
- 第一个压缩事件 t+128s——与起爆点重合;108 次压缩挤在 90 秒窗口;
- diag8 的引擎崩溃(swap 路径空载荷 torch.cat,老病家族的竞态)恰好发生在
  波峰点火时刻——同一场波的最坏抽签;
- 93% 滑移落在压缩事件 ±1.5s 内(波内基线 87%,起爆对齐才是铁证)。

**因果链**:N↑ → 触发线=0.75×pool/N ↓ → 全员在相近的上下文增速下于
~90s 窗口内集中越线(±20% 抖动不足以摊开;40s 到达错峰 ≪ 120s 首压时间,
错峰被增速同质性重新同步)→ 波内后台工作(影子种子预填 + swap 轮的
stage1 重准入/chunk-0 大载荷 + 旧请求退役)挤占周期工作的拍内容量 →
talker 产帧滑 2-3 拍 → 90 秒的迟到风暴。**波过即痊愈(0.0%)。**

**为什么此前九个假设都错**:病灶不在任何单一机件——心跳/CPU/GPU/投递全部
健康——而在"非周期大活的第一次集体到期"这个时间事件上;六轮短测(6 轮
≈ 前 5 分钟)的测量窗恰好就是波窗,把"一场风暴"误读成了"稳态崩溃"。
N 阶梯全部对上:u36 触发线 17.7k 六轮内根本未越线(0.3% 迟到)、u48 轻波
(4%)、u56 全波(15-18%)、u64 更密(21%)。

**修法菜单(对症,未动待令)**:
1. 触发线相位化:准入时确定性铺开到 [0.5,1.0)×份额(现为随机 ×[0.8,1.0)),
   首波密度 ÷3——一行改动;
2. 全局 swap 泄洪闸:同 warmup permits,>K 个 swap 在飞即缓期(waive 机制

**结论**:P9 不设默认。它是把 stage1 的调度墙拆掉的有效手段,但 u64 的下一

## 18. 重复跑纪律:u56 达标结论被第三跑推翻(2026-08-14)

T@u56 三跑:**0.93 / 1.10 / 1.91%**(卡顿 35 / 45 / 67ms),均值 **1.30% /

此处更正。

第三跑不是噪声,是**间歇性故障**,与前两跑有可分辨的差异:后段出现风暴
(第 7/8 个 20s 桶 4.6%、4.4%,前两跑封顶 1.4-2.5%)、迟到从"只在开轮"
溢出到整轮([320,42,30,38] vs [244,1,0,0]),并伴随:

- `unowned_audio = 89`(前两跑均为 0):日志原文 `UNOWNED audio output
  dropped -- audio_seg_fifo is empty, attribution may be shifted` —— 服务端
  收到无法归属的音频并丢弃,客户端表现为迟到/卡顿;
- 同跑一条 `COMPRESS: shadow warm-up abandoned (warm-up timeout); the
  blocking roll remains the fallback` + `blocking_roll = 1`。

**推定链条**:压缩影子预热超时 → 回退阻塞式 roll → 片段记账错位 →

三跑发作一次,发作即吃掉约 1pp。

**因此容量表须按"可靠通过"重写**,T 的可靠点位待定(u36 通过、u56 边界),
补跑 u48×2 中。教训重申:单跑判决在这个系统上不可信,尤其当结果骑在判定
线上时——本次正是靠第三跑才拦下一个过满的结论。

## 20. A*(应用层优化到位的 A):应用动不了这堵墙(2026-08-14)

A* v1 = A + 四项**自查属实**的应用层改动:音频到达即预填充(A 从未开、部分 T
跑开着=原不公平)、帧信箱脱离周期化开关(新 `VLLM_OMNI_FRAME_FLUSH_MS`,
纯 API 服务器代码,不消耗调度器任何东西)、stage2 去 seed+repetition_penalty
(该阶段 temperature=0 贪心,输出不变,只是每轮白建 token 历史张量)、
stage1 去 seed(只影响可复现性,不改分布;repetition_penalty 保留,因为它会
改分布,不是免费项)。配置留档 `deploy_A_star.yaml`,臂定义进 `run_cell.sh`。

**u36 三格对照**:

| | 迟到% | 卡顿ms/轮 | 首字 p50 | **stage1 单轮** | GPU1 |
|---|---|---|---|---|---|
| A 原样 | 18.5 | 877 | 758 | **42.6ms** | 48% |
| A*(应用优化) | 14.0 | 824 | **681** | **42.3ms** | 49% |
| A+引擎修复 | **0.2** | **5.5** | 644 | — | — |

应用层优化改善了首字(预填充移出关键路径),但**决定容量的单轮耗时纹丝不动**
(42.6→42.3ms),GPU 利用率也不动(48→49%)。同一负载下,只改引擎的取数据
方式就把迟到从 14.7% 打到 0.2%。**结论:应用层动不了这堵墙,引擎能。**

**顺带证伪普查的两条**:(1) `renderer_num_workers` 字段在代码中不存在,该条
作废;(2) `active_stream_window` 不是"限制每轮批次"的手段——读码确认它是
**并发流硬上限**:窗口外的会话被整体挂起不服务(`_preempt_non_active_running`
→ `_held_non_active`),对 36 个都要实时出声的会话等于饿死一部分。`max_num_seqs`
同理。**因此 vLLM 配置层根本不提供"批次更小、跑得更勤"这个选项**,只提供会
饿死会话的硬准入上限;要小批次高频率必须改调度器——这正是 T 的节奏器所做的,
也是本工作论点的配置层佐证。

### 20b. 更正:配置层的 CPU/GPU 重叠确实能移动这堵墙

第 20 节结论"应用层动不了这堵墙"**被证伪**。`async_scheduling` 是部署配置
(=应用层可控),在 A* 上打开它,u36:

| u36 | 迟到% | 卡顿ms/轮 | stage1 单轮 | GPU1 |
|---|---|---|---|---|
| A 原样 | 18.5 | 877 | 42.6ms | 48% |
| A*(4 项应用改动) | 14.0 | 824 | 42.3ms | 49% |
| **A* + 标准重叠** | **0.6** | **23** | **24.0ms** | **69%** |
| A + 引擎修复(对照) | 0.2 | 5.5 | — | — |

质量核查通过:216/216 轮、音频 26.2s、文本 399 字(与对照可比)、**全部异常
日志为 0**(EMPTY span / boundary-cap / PARTIAL segment / row shortfall /
UNOWNED 均为 0),未出现部署注释所警告的 -1 哨兵崩溃。

**机制**:park 协议要求"一件载荷占两轮"。活下来有两条路——(1) 取消该税
(引擎修复:一件一轮);(2) 让该税变便宜(重叠:单轮 42.6→24.0ms,两轮
48ms 仍快于 80ms 预算)。路 (2) 属部署配置,因此**应用层确有可用手段**,
且部署注释中"stage1 必须关闭 async_scheduling"的理由在当前代码上不再复现
——本项目长期背着一个基于过时认知的自我限制。

**教训(今日第二次)**:我从"我试过的那几项应用改动无效"推广到"应用层
无能为力",而当时尚未测最有力的那一项。结论的作用域必须等于实测的作用域。

## 21. 公平对撞终局:周期化的净价值不在容量,在过载姿态与开轮(2026-08-14)

两臂配置完全对齐(同应用项、同部署、同负载、同种子),唯一差别是调度策略:

| 负载 | 通用引擎(应用+配置+两处引擎修复) | 周期化引擎 T* |
|---|---|---|
| u48 | 0.39% / 16ms / 首字 800 / 跨度 0.69 | 0.32% / 10ms / **首字 539** / 跨度 0.99 |
| u56 | 3.18% / 118ms / 首字 944 / 跨度 0.86 | **1.82% / 89ms / 首字 788** / 跨度 0.98 |
| u64 | 19.23% / 1052ms / 首字 1081 / 跨度 0.98 | **13.03% / 967ms** / 首字 1074 / 跨度 0.98 |

**结论四条**:

1. **容量(严格 SLO)无优势**:两臂都在 u48 达标、u56 起不达标。此前"周期化
   容量翻倍"的说法,绝大部分应归给两处引擎缺陷的修复(交接税、被迫关闭的
   CPU/GPU 重叠),而非调度策略本身。
2. **过载姿态更优**:每个过载点上周期化的迟到率与卡顿都好 1.5-1.7×
   (u56 1.82 vs 3.18;u64 13.0 vs 19.2)。滑坡更缓、更可预测。
3. **开轮更快**:u48 首字 539 vs 800ms(-33%),u56 788 vs 944ms;代价是
   u56 首字 p99 更差(2174 vs 1520)。
4. **送达体制不同**:周期化恒定贴实时(跨度 0.98-0.99);通用引擎在不饱和时
   抢跑(0.69),饱和后被迫收敛(0.98)。抢跑意味着客户端缓冲不可控、打断时
   已算音频作废——miss/stall 指标看不见这一项。

**观察待验**:T* 在 u56 是 1.82%,而未加重叠/应用项的老配置 T 是 1.06%——
重叠对周期化臂可能有副作用(节奏器本已控批,重叠改变了动态)。单跑,存疑。

**边界**:u64 两臂皆崩而 GPU 仅 67-70%、显存 40/96GB,说明还有第三层软件
瓶颈(声码器与开轮路径),留待后续。

## 23. 臂成员判据:去相关是卫生,造相关才是周期化(2026-08-14,用户裁定)

争议点:帧信箱(帧到达进箱、全局 80ms 拍沿冲刷)此前被我按"代码位置在 API
服务器"归为应用层并给了通用臂。用户指出它出身于 WP7(tick 引擎那轮),开关
本就绑在 tick 时钟上,且普通应用作者不会自发这么写——应归 T。

**判据由此收敛为一句**:

- **打散(去相关)**——把本来会同时发生的事件错开(压缩触发相位梯、预热
  全局日历):任何多租户系统都欠用户的基本卫生,**归基线**;
- **造相关**——把本来各自随机到达的事件按共享时钟凑到同一时刻以便合批
  (帧信箱):**这就是周期化思想本身**,只是作用在输入边界,**归 T**。

出身可作线索,机理才是判据:准入台账(P3)出身于 live-vllm 那轮,但机理是
容量规划(池份额/槽位账)而非时间节奏,**仍归基线**;音频到达即预填充
(commit b5f1024f,2026-08-09,早于 tick 引擎四天)机理是"数据到就干活"
而非"按拍干活",**归基线**。

**已入库改动**:`run_cell.sh` 的 Astar/AstarFix 臂移除 `FRAME_FLUSH_MS`。
**对已有数据的影响**:`Fair_A56`(1.17%)是带帧信箱跑的,按新定义通用臂应
更差,故第 22 节报的 3.5×/7.7× 是**保守值**,方向不变。待补一格(通用臂去
帧信箱 @u56)可给出该项单独价值。
